# Options patterns

Module factories share names, but not identical option shapes or lifecycle
behavior. This matrix records which factories exist; consult the owning module
for required providers and side effects. The relay is constructed directly.

<span class="module-badge">built-in · @omnitron-dev/titan · config + logger</span>

Built-in modules follow the same pattern:

| Module     | `forRoot` | `forRootAsync` | `forFeature` |
| ---------- | :-------: | :------------: | :----------: |
| `config`   |     ✓     |       ✓        |       ✓      |
| `logger`   |     ✓     |       ✓        |       —      |

`ConfigModule.forFeature(name, schema?)` exports a provider for the named
configuration subtree and validates it when a schema is supplied. It does not
load a separate configuration source.

## `forRoot(options)` — synchronous configuration {#forrootoptions--synchronous-configuration}

The simplest form. Options are known at boot time.

```typescript
@Module({
  imports: [
    TitanRedisModule.forRoot({
      config: { host: 'localhost', port: 6379, db: 0 },
    }),
    TitanCacheModule.forRoot({
      defaultTtl: 60,
      maxSize:    10_000,
    }),
  ],
})
class AppModule {}
```

Use when:
- Options come from a literal object or `process.env` read.
- No other module's services need to compute the options.

## `forRootAsync({ useFactory, inject?, imports? })` — DI-driven {#forrootasync-usefactory-inject-imports---di-driven}

When the options depend on another module's service — most often
`ConfigService` — use the async variant.

```typescript
import { TitanRedisModule } from '@omnitron-dev/titan-redis';
import { CONFIG_SERVICE_TOKEN, ConfigService }
  from '@omnitron-dev/titan/module/config';

@Module({
  imports: [
    TitanRedisModule.forRootAsync({
      useFactory: (config: ConfigService) => ({
        config: {
          host: config.get('redis.host'),
          port: config.get('redis.port'),
          db:   config.get('redis.db'),
        },
      }),
      inject: [CONFIG_SERVICE_TOKEN],
    }),
  ],
})
class AppModule {}
```

The factory:
- Receives the injected dependencies in the order declared in `inject`.
- Returns the same `options` shape as `forRoot()`.
- May be sync or async (`async (config) => {...}` is fine).

### Importing extra modules into the factory scope {#importing-extra-modules-into-the-factory-scope}

If your factory depends on services that aren't globally exported,
import their host module:

```typescript
TitanCacheModule.forRootAsync({
  imports: [SecretsModule],                    // brings SecretsService into scope
  useFactory: (secrets: SecretsService) => ({
    redis: { url: secrets.get('REDIS_URL') },
  }),
  inject: [SecretsService],
}),
```

### `useClass` / `useExisting` variants {#useclass--useexisting-variants}

Some modules also accept class-based provider variants:

```typescript
NotificationsModule.forRootAsync({
  useClass: NotificationsOptionsFactory,       // implements `createNotificationsOptions(): Options`
})

// Or reuse an existing factory exported by another module:
NotificationsModule.forRootAsync({
  useExisting: SharedOptionsFactory,
})
```

Refer to per-module pages — `useClass` and `useExisting` are
supported by `titan-notifications` but not uniformly by all
modules.

## `forFeature(...)` — register additional resources {#forfeature--register-additional-resources}

`forFeature` is for *adding* per-feature configuration **after**
the global module has been bound. Shape varies per module.

### `titan-database.forFeature(repositories)` {#titan-databaseforfeaturerepositories}

```typescript
@Module({
  imports: [
    TitanDatabaseModule.forFeature([
      UsersRepository,
      OrdersRepository,
    ]),
  ],
})
class UsersModule {}
```

Each repository becomes injectable by class reference; the
underlying `Database` connection is the one registered by the
global `TitanDatabaseModule.forRoot(...)`.

### `titan-cache.forFeature(caches)` {#titan-cacheforfeaturecaches}

```typescript
@Module({
  imports: [
    TitanCacheModule.forFeature([
      { name: 'users',  defaultTtl: 300 },
      { name: 'tokens', defaultTtl: 60  },
    ]),
  ],
})
class CacheLayerModule {}
```

Each name resolves its own cache configuration. Sharing an L2 backend requires
explicit adapter options; named caches do not automatically share one store.

### `titan-events.forFeature({ events, schemas })` {#titan-eventsforfeatureemitters}

The actual signature is `EventsModule.forFeature({ events?, schemas? })`. It
registers feature-local symbols containing those values, but the current discovery
and validation services do not consume them. It is not a provider-discovery API.
Register listener classes as ordinary providers and register/validate schemas
explicitly through `EventValidationService`.

### `titan-health.forFeature(indicators)` {#titan-healthforfeatureindicators}

Registers additional `IHealthIndicator` classes after `forRoot`:

```typescript
@Module({
  imports: [
    TitanHealthModule.forFeature([
      StripeHealthIndicator,
      SearchClusterIndicator,
    ]),
  ],
})
class FeatureModule {}
```

### `titan-redis.forFeature(clients)` {#titan-redisforfeatureclients}

Adds named Redis clients:

```typescript
@Module({
  imports: [
    TitanRedisModule.forFeature(['cache', 'queue']),
  ],
})
class MultiClientModule {}
```

Inject via the token factory:

```typescript
import { getRedisClientToken } from '@omnitron-dev/titan-redis';

constructor(
  @Inject(getRedisClientToken('cache')) private cacheRedis: Redis,
  @Inject(getRedisClientToken('queue')) private queueRedis: Redis,
) {}
```

### `titan-scheduler.forFeature(providers)` {#titan-schedulerforfeatureproviders}

Registers additional providers that own `@Cron` / `@Interval` /
`@Timeout` methods, ensuring the scheduler discovers them.

## `forWorker(...)` — separate runtime {#forworker--separate-runtime}

`NotificationsModule.forWorker` binds application target resolver, persister and
realtime signaler tokens and registers `NotificationWorkerService`. It does not
create a transport, start a consumer or implement SMTP/SMS/push delivery.

The application calls `worker.start(rawRedis, options?)` after its dependencies
are ready and awaits `worker.stop()` before closing that caller-owned connection.
This worker consumes the `NotificationEvent` schema published by
`NotificationPublisher`; it is not a deferred version of `NotificationsService.send`.
See the [notification worker guide](./notifications.mdx#quickstart--worker-the-pod-that-consumes-and-delivers).

## Global vs scoped modules {#global-vs-scoped-modules}

Most modules accept `isGlobal: true` (or `global: true` on the
returned `DynamicModule`) — when set, the module's exports are
visible to every other module without explicit re-import.

```typescript
TitanRedisModule.forRoot({ config, isGlobal: true });
```

| When                                              | Recommendation                  |
| ------------------------------------------------- | ------------------------------- |
| Infrastructure (config, logger, redis, database)  | `isGlobal: true`                |
| Feature modules (your business logic)             | leave scoped                    |
| Test environments                                 | scoped — easier to override     |

## Async lifecycle of `forRootAsync` {#async-lifecycle-of-forrootasync}

```mermaid
sequenceDiagram
  participant App as Application.create
  participant Container as DI container
  participant Factory as useFactory
  participant Module as TitanXModule

  App->>Container: resolve dependency graph
  Container->>Container: resolve inject[] tokens
  Container->>Factory: call useFactory(...deps)
  Factory-->>Container: options
  Container->>Module: instantiate with resolved options
  Module->>Container: bind exports
  App->>Module: onInit / onStart
```

The factory is called **once** per app boot, after its declared
`inject:` dependencies are resolved. The resolved options are then
used to instantiate the module's services.

## Common gotchas {#common-gotchas}

- **`inject:` order must match factory arguments.** A misordered
  array silently passes the wrong service to the wrong parameter.
  Prefer named destructuring + tuple typing:
  ```typescript
  useFactory: (config: ConfigService, redis: RedisManager) => ({...}),
  inject: [CONFIG_SERVICE_TOKEN, REDIS_MANAGER],
  ```
- **`forFeature` before `forRoot`** — the global module has to be
  bound first or `forFeature` won't find what to attach to.
  `Application.create({ modules: [GlobalModule, FeatureModule] })`
  resolves order from the dependency graph, but if you're loading
  them in `imports: []` manually, list `forRoot` first.
- **Assuming one Redis registration wires every module.** Lock and discovery
  can use the manager, notifications may create dedicated connections, and cache
  needs an adapter. Follow each module's connection contract.
- **Calling `forRoot` twice.** Factories can register the same tokens; do not
  rely on an undocumented last-call-wins rule. Use named resources supported by
  the package and explicit test overrides.
- **`forRootAsync` factory throwing.** A throw aborts boot — the
  error propagates out of the container's async resolution (the
  Nexus DI layer raises `ResolutionError` / `AsyncResolutionError`
  for resolution failures). Don't log-and-swallow; let it crash so
  the operator sees the configuration mistake.

## Migration tip — sync to async {#migration-tip--sync-to-async}

Start with `forRoot({...})`. The moment you need a value from
`ConfigService` (or any other service), switch the call to
`forRootAsync({useFactory, inject})`. The options object shape
stays identical — only the wrapper changes.

```typescript
// Before
TitanRedisModule.forRoot({ config: { url: 'redis://localhost' } })

// After
TitanRedisModule.forRootAsync({
  useFactory: (cfg: ConfigService) => ({ config: { url: cfg.get('redis.url') } }),
  inject:     [CONFIG_SERVICE_TOKEN],
})
```
