# Observability matrix

This reference distinguishes values a caller can read, events from a particular
object, and integration that application code must install. A `getStats` method
is not an automatic `titan-metrics` exporter, and an exported health indicator is
not automatically registered by another module.

## At-a-glance {#at-a-glance}

| Package | Read/observe | Integration boundary |
| --- | --- | --- |
| `titan-auth` | JWT verification result/errors, `getCacheStats()` | No automatic metric exporter |
| `titan-cache` | Per-cache/global stats and cache events; health helper classes | Register/bridge explicitly |
| `titan-database` | Connection/query failures and configured instrumentation | Database health indicator is in `titan-health` |
| `titan-discovery` | Discovery events and heartbeat/registration logs | Pub/sub must be enabled; integration startup can fail independently |
| `titan-events` | `getStatistics()`, configured emitter history | In-process observations |
| `titan-health` | `check`, `checkOne`, `isReady`, `isAlive` | Pull-based; no health-change event or HTTP listener |
| `titan-lock` | Acquire/renew/release results, FailureTracker logs | No metric exporter or release-all lifecycle hook |
| `titan-lumen` | Published document service results and errors | Host owns operational telemetry |
| `titan-mailer` | Send result, outbox status/health, delivery observer | SMTP acceptance is not inbox delivery |
| `titan-metrics` | History/snapshot, registry text, storage status | Explicit business/RPC recording and SQL wiring |
| `titan-notifications` | Send outcomes, transport diagnostics, supplied health indicator | Distinct producer/channel/event-worker contracts |
| `titan-pm` | Manager, supervisor and pool events; process metrics | Subscribe to the object that emits the event |
| `titan-ratelimit` | Check result, `getStats()`, tier stats | No automatic dashboard/exporter |
| `titan-redis` | Managed connection state and errors | Health indicator needs a passed client |
| `titan-scheduler` | Registry events and `getMetrics()` | Application bridges to external storage |
| `titan-storage` | Per-operation results/errors and `getStorageInfo()` | Usage readings are not atomic quotas |
| `titan-telemetry-relay` | `stats()` including delivery error and loss counters | No built-in external sink or automatic module subscription |

Config exposes `onChange`; Logger exposes structured records, sink health and
flush status. These signals have separate ownership and persistence.

## Per-module reference {#per-module-reference}

### `titan-pm` — process observations {#titan-pm--the-most-chatty-module}

`ProcessManager` emits process lifecycle events such as `process:crash`.
`ProcessSupervisor` and a pool have their own emitters; their child/pool events
are not all forwarded through the manager. Subscribe to the object returned by
the API you use. `ProcessManager.getMetrics(processId)` asks the worker proxy for
process readings and can return null.

```typescript
pm.on('process:crash', (info, error) => {
  logger.error({ processId: info.id, error }, 'child crashed');
});
```

A health event, a worker's responsiveness and completion of a particular request
are different observations. See [PM](./pm.mdx) for supervision and pool admission.

### `titan-notifications` {#titan-notifications}

`NOTIFICATIONS_EVENTS` names lifecycle topics on an optional `EventsService`.
Transport topics consumed by `@OnNotification` are a different channel. The host
must register decorated handlers; metadata alone does not create a subscription.

Resolve `NOTIFICATIONS_HEALTH` and register that indicator explicitly with
`HealthService`. It includes transport and observer failures. Send status,
per-channel status, database persistence and recipient delivery are distinct
boundaries. The standalone event worker's poison-message handling is not the
same as Rotif's DLQ. See [notifications](./notifications.mdx).

### `titan-discovery` {#titan-discovery}

The service logs registration, heartbeat failures and shutdown. With pub/sub
enabled it emits `discovery:event` for received registry events. Default pub/sub
is disabled. A stopped heartbeat and Redis TTL govern registry staleness; this
is not a health probe of the application handler.

The module attempts Netron integration separately and can continue when that
initialization fails. Check the discovery and Netron paths independently.

### `titan-events` {#titan-events}

`EventsService.getStatistics(event?)` reports its in-memory event counts and
handler observations. When emitter history is enabled, `getHistory` and
`replayEvents` operate on that emitter's retained memory. `EventHistoryService`
is an additional exported service; its existence does not make history durable.
Await async emission to observe handler rejection. Application effects already
committed are not rolled back by a failed handler.

### `titan-scheduler` {#titan-scheduler}

`SchedulerService.getMetrics()` reads scheduler metrics when available. The
registry publishes scheduler/job events; startup logs discovered job counts.
None of these automatically writes to `titan-metrics`.

Observe that the expected job was registered, that a scheduled fire ran, and that
its business effect committed. Those observations cannot be inferred from a
running scheduler or a Redis lock alone.

### `titan-cache` {#titan-cache}

Read `cache.getStats()` or `CacheService.getGlobalStats()` and subscribe through
`CacheService.on(...)` to the cache events it forwards. Stats are local to the
process. An L2 miss can mean missing data or a backend failure; some L2 operations
catch failures. Do not interpret hit rate as backend availability.

The package exports `CacheHealthIndicator` and `MultiTierCacheHealthIndicator`.
Wire the chosen helper explicitly; importing cache and health modules does not
perform that registration.

### `titan-lock` {#titan-lock}

The service uses Titan's `FailureTracker` to report repeated Redis failures and
recovery rather than logging every identical error. An acquire returns an owner
ID or no lease; callers must also handle renewal/release failure. These are
coordination readings, not evidence that an external effect happened once.
No metric exporter is installed.

### `titan-database` {#titan-database}

Query failures propagate through the database API. Logging and query/transaction
instrumentation depend on the manager configuration and selected path. Use the
`DatabaseHealthIndicator` exported by `titan-health` with the actual connection;
it is not an export or automatic provider of `titan-database`.

A successful connectivity check does not establish schema readiness, a migration
result or a business transaction's durable outcome. Use the database readiness
and transaction APIs for their respective checks.

### `titan-redis` {#titan-redis}

The manager reports connection/reconnect/errors through its configured logger.
Use `RedisHealthIndicator` with the selected client for an on-demand check.
Connection readiness does not establish that a notification was routed, a stream
retained it or a lock is still owned. Observe the consuming module's operation.

### `titan-auth` {#titan-auth}

`JWTService.getCacheStats()` exposes verification-cache readings. Verification
errors and key/JWKS initialization can be logged through the configured logger.
The cache is local and no metrics exporter is installed. Cache eviction/expiry
is not token revocation; session authority checks are a separate path.

### `titan-ratelimit` {#titan-ratelimit}

`RateLimitService.getStats()` and tier statistics expose local checks, allowed
and denied counts. Check results carry allowance and retry/reset information.
The Redis storage reports connection errors through its logger, but this is not
a guaranteed per-denial log stream or an automatic metrics integration.

### `titan-metrics` {#titan-metrics}

<span class="module-badge">official · @omnitron-dev/titan-metrics</span>

`MetricsService.getStorageStatus()` reports durability, queue samples/bytes,
completed writes, retry failures, known losses and retention/callback errors.
Background errors also reach `onError`; explicit write/flush failures reject.
Omnitron records rate-limited structured failures and exposes the same reading
through daemon health, CLI and Console. Normal successful flushes stay quiet.

The process collector (`collection: { process: true }`) records, for
the daemon's own process: `heap_used_bytes`, `heap_total_bytes`,
`rss_bytes`, `external_bytes`, `cpu_percent`, `uptime_seconds`. The
child/orchestrator collector (`system: true`) additionally records
`memory_bytes`, `rpc_requests_total`, `rpc_errors_total`, and
`app_status` per supervised app. Event-loop lag is not collected by
the built-in collector.

### `titan-telemetry-relay` {#titan-telemetry-relay}

Read `stats()` for `totalEmitted`, `totalSent`, `totalFailed`, `totalReceived`,
`transportConnected`, `lastError`, buffer drops and WAL retention/eviction data.
The service does not automatically publish these to Titan metrics. It extends an
event emitter, but that inheritance is not a documented stream of WAL events.

Read [delivery and recovery](./telemetry-relay.mdx#delivery-and-recovery) before
interpreting a buffered entry, WAL record or acknowledgement as durable delivery.

### `titan-health` {#titan-health}

`check()` returns worst-status aggregation, per-indicator results, timestamp,
aggregate latency and uptime. `checkOne()` returns an indicator result. Individual
latency/details depend on the indicator.

The service converts indicator failures/timeouts into unhealthy results; it does
not emit `health:changed`, log every degraded result or export check latency.
Poll it and route observations explicitly. A timeout does not cancel arbitrary
work inside the indicator.

### `titan-mailer` {#titan-mailer}

`PostgresMailOutbox.status`, `failed` and `health` describe the durable queue.
`onDelivery` reports committed outcomes without message content. The application
forwards those events to Logger; they are separate from SMTP inbox delivery.

### `titan-storage` {#titan-storage}

Inspect operation results and per-key errors from `deleteMany`. `getStorageInfo`
returns backend usage data; S3 usage is cached and is not an atomic quota check.

### `titan-lumen` {#titan-lumen}

Observe the actual document/access/live-edit RPC results. The module supplies no
automatic metrics exporter or health indicator; the host wires its operational
checks around the configured corpus and authoring store.

## Built-in modules {#built-in-modules}

### `config` {#config}

<span class="module-badge">built-in · @omnitron-dev/titan/module/config</span>

Change notifications are delivered through a callback subscription,
not a named event-bus topic:

```typescript
const unsubscribe = config.onChange((event: IConfigChangeEvent) => {
  // event: { path, oldValue, newValue, source, timestamp }
});
```

Notable logs:
- `info` — `Configuration reloaded due to file change` (after a watched source changes)
- `error` — `Failed to reload configuration`

### `logger` {#logger}

`LoggerService.getSinkHealth()` reports sink errors, dropped/unconfirmed bytes
and delivery state; `flush()` awaits configured delivery barriers and reports
failure. Read those receipts when persistence matters. JSON output alone is not
evidence that a downstream file/database/exporter accepted the record.

Use `createNullLogger()` only when discarding logs is intentional, such as a
focused unit test. Configure processors and destinations explicitly.

## Cross-cutting recommendations {#cross-cutting-recommendations}

### Subscribe instead of poll {#subscribe-instead-of-poll}

Use subscriptions where the owning object emits the event and polling where
only a snapshot API exists. A pool event belongs to the pool, a supervisor child
event to the supervisor, and a health result to an explicit check. Do not invent
an event name from the corresponding method or result status.

### Tie metrics to events {#tie-metrics-to-events}

An application can bridge a known event to a custom observation:

```typescript
pm.on('process:crash', () => {
  metrics.recordTyped('counter', 'worker_crashes_total', { app: 'worker-fleet' }, 1);
});
```

The registry accumulates this counter; history queues the supplied increments.
Flush before reading recent history. The bridge is application code, and repeated
subscription would double-count events.

### Alert thresholds — common starting points {#alert-thresholds--common-starting-points}

Set thresholds from workload measurements and failure budgets rather than a
universal CPU/RSS percentage. Useful conditions include nonzero storage loss,
failed durable writes, growing pending age, repeated worker replacement, missing
scheduled completion and retained terminal mail failures. Define the observation
window and recovery condition for each alert. No alerting backend is installed
by this reference.

### Don't log per-call by default {#dont-log-per-call-by-default}

Several modules (`titan-ratelimit`, `titan-cache`, `titan-auth`)
intentionally stay quiet at info level. Per-call logging at request
rate is a recipe for disk/SIEM saturation. Use counters and
sampled debug logging instead.
